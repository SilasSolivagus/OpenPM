# 07 · Iterate Skills（双盲评分与自我迭代）

## 目标
让整套 OpenPM 体系在真实公司业务中**越干越丝滑**——持续降低 PM 在上 Wiki 前需要手动删改重排的比例，最终让 PM 只需要投入：**对业务的理解 + 对公司情况的判断 + 个人的 Taste 与决策力**。

---

## 一、 双盲 A/B 对比实验与量化度量

每当修改 `skills/02~06` 的规范或模板时，禁止仅凭主观感觉合入，必须执行：
1. **抽取盲测样本**：从 `evals/test-cases/` 及脱敏的历史项目中抽取 2–3 个代表性项目；
2. **双盲生成**：分别用「基线版本 Skill」与「候选新版 Skill」跑出结果，隐藏版本号（标记为方案 A / 方案 B）；
3. **独立裁判打分（10 分制）**：按以下维度由独立裁判 Agent 盲评打分：
   - 逻辑完整性与异常分支覆盖度；
   - 原型骨架与公司/端型习惯贴合度（严格遵守纯灰阶 `wt-*`）；
   - 契约与格式合法性（如 `preflight_check.py`、Confluence Storage XML / 嵌套子表 0 破表）；
   - **核心北极星指标**：预估「上 Wiki 前 PM 需手动删改重排的比例（%）」。

---

## 二、 人机协同确认（`AskUserQuestion`）与数据集分流

1. **定期汇报与裁决**：向 PM 汇报实验报告（含均分对比、手动改写率变化及具体微调建议），通过 **`AskUserQuestion`** 让 PM 决定：**「改不改、改哪几条」**。
2. **严格分流两层数据集（防止过拟合）**：
   - **项目业务改点**（如“把滑块改成整宽”、“金额阈值改成 5 万”）→ 写入 `evals/datasets/project-decisions.jsonl`，只影响当前项目 PRD 与原型；
   - **Skill 通用缺陷 / 个人 Taste**（如“减少过度表格化”、“按钮文案偏好用『确认提交』”）→ 写入 `evals/datasets/skill-defects.jsonl`，用于迭代 `skills/` 与更新回归测试集。
